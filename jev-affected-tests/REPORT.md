# Jev를 affected_tests에 쓸 수 있는가 — 검증 보고서

2026-09-21 · 대상 모델 `jev-1.13.0` · 대상 프로젝트 Mastodon(`1d4c2c567`) · 정답지는 [affected_tests](https://github.com/riseshia/affected_tests)의 coverage 엔진으로 실측

## 결론부터

**Jev는 코드만 읽고도 "이 spec이 이 소스를 실행하는가"를 꽤 잘 맞힌다. 그래도 affected_tests의 선택 로직을 대신할 수는 없고, 쓸 자리는 "맵에 없는 파일이 바뀌었을 때의 보조 순위" 하나다.**

| 질문 | 답 |
|---|---|
| 텍스트만으로 의존 관계를 읽어내는가 | 읽어낸다. AUC 0.87–0.90. grep 수준 기준선(0.55)을 크게 앞서고, 간접 의존에서는 Claude Sonnet과 같은 수준이다 |
| 맵을 대체할 수 있는가 | 없다. 맵은 실측이고 Jev는 추정이다. 영향받는 spec의 95%를 잡으려면 스위트의 31%를 돌려야 하고, 그래도 5%는 놓친다 |
| 놓쳐도 되는 자리(빠른 피드백용 순서)에는 쓸 만한가 | 쓸 만하다. 스위트의 5%만 먼저 돌려도 영향받는 spec의 68%가 그 안에 들어온다 |
| 어디가 약한가 | 라우팅 헬퍼, 버전 상수, 커넥션 풀처럼 **호출 사슬 깊숙이 있어서 spec 본문에 흔적이 없는 기반 코드** |
| 실제로 돌릴 만한 비용인가 | 그렇다. spec 여러 개를 한 요청에 묶으면 바뀐 파일 하나에 대해 스위트 전체(739개)를 줄 세우는 데 요청 27회, 2초, $0.025다. 묶어도 정확도는 떨어지지 않는다 |

실험 전에는 "Jev는 구조가 아니라 내용어로 읽으니 간접 의존은 못 잡을 것"이라고 예상했다. 이 예상은 틀렸다.
이름이 전혀 안 닮은 간접 의존에서도 AUC 0.90이 나왔다.

## 1. 무엇을, 왜 확인했나

affected_tests는 테스트를 실제로 돌리면서 "어떤 spec이 어떤 소스 파일을 실행했는가"를 기록해 맵을 만들고,
diff에 들어 있는 파일을 그 맵에서 찾아 돌릴 spec을 고른다. 맵에 있는 파일에 대해서는 이보다 정확한 방법이 없다.

틈은 **맵에 없는 파일**이다. `Differ`는 이런 파일을 조용히 건너뛴다(`lib/affected_tests/differ.rb`에서 확인).

- 수정된 파일이 맵에 없으면 `map[path] || []`라서 spec이 0개 선택된다. 맵을 만든 리비전 이후에 생긴 파일이 여기 해당한다.
- 추가된 파일은 정책상 무시한다. 보통은 그 파일을 부르도록 고친 기존 파일이 맵에 있어서 문제가 없지만,
  이름 규칙으로 자동 로드되는 파일은 부르는 쪽을 고치지 않아도 실행된다.

Jev는 글을 생성하지 않고 "주어진 내용에 대해 이 명제가 참인가"를 0–1 값으로 답하는 모델이다.
그래서 확인할 질문은 하나다. **소스 파일과 spec 파일의 본문만 주고 "이 spec을 돌리면 이 소스의 코드가 실행되는가"를 물었을 때,
그 값이 실측 맵과 얼마나 맞는가.**

## 2. 방법

### 정답지

Mastodon의 RSpec 스위트를 affected_tests(coverage 엔진)를 붙여 한 번 돌렸다. 6,726개 예제, 16분.

- 브라우저가 필요한 `spec/system`은 뺐다.
- 실패한 예제가 있는 spec 파일 132개는 정답지에서 뺐다. 실패한 spec은 중간에 멈추므로 "실행 안 됨"을 믿을 수 없다.
  실패 원인은 대부분 프런트엔드 자산을 빌드하지 않아 HTML 렌더링이 깨진 것이고, 일부는 libvips를 스텁으로 대체한 탓이다.
- 추적을 켜기 전에 애플리케이션 전체를 미리 로드했다. 그러지 않으면 어떤 파일을 처음 autoload한 spec에만 그 파일이 붙어서,
  정답이 실행 순서에 따라 달라진다.
- 남은 정답지는 spec 739개 × 소스(`app/`, `lib/`의 `.rb`) 943개다. spec 하나가 실행하는 소스는 중앙값 31개, 최대 145개다.

### Jev에 묻는 방식

쌍 하나에 요청 하나다. `state`에 소스 경로·소스 본문·spec 경로·spec 본문을 넣고, `noul` 질문
"Running this RSpec test file executes code defined in the source file."을 던진다.
파일은 20,000자에서 자른다(1,682개 중 11개만 해당).

### 기준선

- **spec 본문에 클래스 이름이 나오는가**: `account_policy.rb`면 spec에 `AccountPolicy`가 있는지 본다. grep으로 되는 수준이다.
- **그 소스를 실행하는 spec의 비율**(실험 1): 맵에서 나오는 사전 확률이다. 맵에 없는 파일에는 쓸 수 없으므로 참고용이다.
- **그 spec이 실행하는 소스의 수**(실험 2): 애플리케이션의 절반을 건드리는 통합 spec을 위로 올린다. 새 파일에도 쓸 수 있다.
- **Claude Sonnet**: 텍스트에서 읽어낼 수 있는 상한을 보려는 것이다. 실험 1의 앞 40개 spec에만 적용했다.

### 통계

AUC는 "실행된 쌍 하나와 실행 안 된 쌍 하나를 무작위로 뽑았을 때 실행된 쪽의 값이 더 높을 확률"이다. 0.5면 찍는 것과 같다.
대괄호 안은 95% 구간이고, spec(실험 1) 또는 소스(실험 2) 단위로 다시 뽑는 부트스트랩 500회로 구했다.
같은 파일을 공유하는 쌍들은 서로 독립이 아니기 때문이다.

## 3. 실험 1 — 쌍 단위 순위

spec 300개를 뽑고, spec마다 실행된 소스 8개와 실행 안 된 소스 8개를 뽑았다. 모두 4,505쌍이다.

- 양성은 세 종류로 나눴다. **이름이 맞는 짝**(`account_spec.rb` ↔ `account.rb`, 116쌍),
  **어디서나 쓰이는 파일**(spec의 절반 이상이 실행하는 21개 소스, 1,033쌍), 그 밖의 **간접 의존**(984쌍)이다.
- 음성은 두 종류다. **이웃**은 그 spec이 실제로 쓰는 소스와 같은 디렉터리에 있지만 실행되지 않은 파일(1,172쌍),
  **무관**은 나머지다(1,200쌍).

| 양성 | 음성 | Jev | 클래스 이름 grep | 사전 확률(참고) |
|---|---|---|---|---|
| 전체 | 전체 | **0.871** [0.860, 0.881] | 0.549 | 0.932 |
| 전체 | 이웃 | 0.821 [0.804, 0.836] | 0.548 | 0.906 |
| 전체 | 무관 | 0.921 [0.912, 0.930] | 0.549 | 0.956 |
| 이름이 맞는 짝 | 전체 | 1.000 [1.000, 1.000] | 0.963 | 0.516 |
| 간접 의존 | 전체 | **0.901** [0.888, 0.913] | 0.539 | 0.912 |
| 간접 의존 | 이웃 | 0.858 [0.841, 0.875] | 0.539 | 0.873 |
| 어디서나 쓰이는 파일 | 전체 | 0.829 [0.812, 0.843] | 0.511 | 0.996 |
| 어디서나 쓰이는 파일 | 이웃 | 0.765 [0.740, 0.786] | 0.510 | 0.994 |

- **이름이 맞는 짝은 완벽하게 맞힌다.** 다만 이건 경로 규칙으로도 되는 일이다.
- **간접 의존에서 0.90이다.** grep은 0.54로 사실상 찍는 수준이다. 실행된 소스의 대부분은 spec 본문에 이름이 나오지 않기 때문이다.
  Jev는 이름이 없어도 "이 서비스 spec은 이 모델과 이 concern을 거칠 것"을 읽어낸다.
- **같은 디렉터리의 이웃을 걸러내는 일은 더 어렵다.** 0.86으로 떨어진다.
- **어디서나 쓰이는 파일에 가장 약하다.** `Redisable`, `Account`, `UniqueUsernameValidator` 같은 것들이다.
  대부분 팩토리가 계정을 만들 때 실행되므로 spec 본문에는 흔적이 없다.
  이런 파일은 사전 확률이 0.996으로 완벽하게 잡는다. 맵에 있는 파일이라면 Jev를 쓸 이유가 없다는 뜻이기도 하다.

### Claude Sonnet과의 비교 (앞 40개 spec, 618쌍)

| 양성 | Jev | Claude Sonnet |
|---|---|---|
| 전체 | 0.870 [0.844, 0.896] | 0.925 [0.907, 0.944] |
| 간접 의존 | 0.903 [0.881, 0.926] | 0.908 [0.873, 0.938] |
| 어디서나 쓰이는 파일 | 0.811 [0.769, 0.849] | 0.940 [0.912, 0.964] |

간접 의존에서는 구분이 안 된다. 차이는 어디서나 쓰이는 파일에서 난다.
추정: Claude는 "팩토리로 계정을 만들면 이 코드들이 돈다"는 상식을 쓰고, Jev는 눈앞의 두 파일만 본다.
같은 조건의 비교는 아니다. Claude는 한 spec의 후보 소스 16개를 나란히 보고 답했고, Jev는 쌍마다 따로 답했다.

### 답이 흔들리는 정도

같은 200쌍을 다시 물었을 때 값의 차이는 평균 0.012, 최대 0.11이었다. 순위를 뒤집을 크기가 아니다.

## 4. 실험 2 — 맵에 없는 파일이 바뀌었다면

affected_tests에 끼울 때의 모양 그대로 쟀다. 소스 40개를 뽑아 맵에 없는 파일인 척하고,
소스마다 실제로 실행하는 spec(최대 40개)과 실행하지 않는 spec 150개를 Jev 값으로 줄 세웠다.
어디서나 쓰이는 파일과, 실행하는 spec이 5개 미만인 파일은 뺐다.

"스위트의 10%"는 실행하지 않는 spec 중 10%가 같이 딸려 오는 지점에서 끊었다는 뜻이다. 소스 40개의 평균이다.

| | Jev | 클래스 이름 grep | spec이 실행하는 소스의 수 |
|---|---|---|---|
| AUC | **0.901** [0.861, 0.929] | 0.577 | 0.797 |
| 스위트의 5%만 돌릴 때 잡는 비율 | **68%** [59, 76] | 18% | 33% |
| 스위트의 10% | **75%** [66, 83] | 24% | 48% |
| 스위트의 20% | **82%** [74, 88] | 33% | 64% |
| 95%를 잡는 데 필요한 스위트 비율 | **31%** [23, 43] | 90% | 50% |

새 파일의 자기 spec(이름이 맞는 짝)은 어차피 작성자가 같이 올린다. 그걸 빼고 다시 계산해도
AUC 0.895, 10%에서 74%, 95%에 필요한 비율 35%로 거의 같다.
grep과 Jev를 합친 점수(이름이 나오면 위로, 그 안에서 Jev 순)는 Jev 단독과 차이가 없었다.

### 컷오프 하나로 자른다면

위 표는 소스마다 끊는 지점을 따로 잡은 것이다. 실제 도구는 모든 파일에 같은 컷오프를 써야 한다.

| 컷오프 | 영향받는 spec 중 선택되는 비율 | 무관한 spec 중 선택되는 비율 |
|---|---|---|
| Jev ≥ 0.05 | 98.8% | 79.9% |
| Jev ≥ 0.10 | 93.9% | 47.6% |
| Jev ≥ 0.20 | 76.6% | 21.8% |
| Jev ≥ 0.30 | 65.8% | 12.0% |
| Jev ≥ 0.50 | 46.5% | 2.0% |

안전한 쪽(놓치는 게 1% 남짓)으로 가면 스위트의 80%를 돌려야 해서 "전부 돌리기"와 다를 게 없다.
절반만 돌리면 6%를 놓친다.

### 어떤 파일에서 틀리는가

소스별 AUC는 0.63에서 1.00까지 퍼져 있다. 아래쪽에 있는 것들이다.

| AUC | 실행하는 spec 수 | 소스 |
|---|---|---|
| 0.632 | 342 | `app/helpers/routing_helper.rb` |
| 0.690 | 20 | `app/lib/connection_pool/shared_connection_pool.rb` |
| 0.694 | 7 | `app/lib/plain_text_formatter.rb` |
| 0.698 | 64 | `lib/mastodon/version.rb` |
| 0.727 | 6 | `app/services/fetch_link_card_service.rb` |
| 0.777 | 21 | `app/helpers/database_helper.rb` |

반대로 `follow_service.rb`, `bookmark.rb`, `api/pagination.rb`, `status_reach_finder.rb` 같은
도메인 코드는 0.99 이상이다. 40개 중 23개가 0.93을 넘는다.
틀리는 쪽은 **여러 곳에서 간접적으로 불리는 기반 코드**로 모인다. 하필 바뀌었을 때 영향 범위가 가장 넓은 종류다.

## 5. 실험 3 — 실제로 돌리는 모양 그대로

실험 2의 방식(쌍 하나에 요청 하나)을 그대로 쓰면 바뀐 파일 하나에 spec 수만큼 요청이 나간다.
Mastodon이면 874회, 분당 1,200회 한도로 45초다. 파일이 여럿이면 분 단위가 된다.
Jev는 요청 하나에 질문을 여러 개 받을 수 있으므로, `state`에 소스 하나와 spec 여러 개를 넣고 spec마다 질문을 하나씩 달았다.

### 1단계: 한 요청에 몇 개까지 묶어도 되는가

평가에 쓰지 않는 소스 10개로 골랐다. 기준은 결과를 보기 전에 정했다.
"쌍 하나에 요청 하나일 때보다 평균 AUC가 0.02 넘게 떨어지지 않는 가장 큰 묶음."
`state`가 32k 토큰을 넘으면 거절되므로, 개수 상한과 별개로 90,000자에서 끊는다.

| 한 요청의 spec 수 | AUC | 소스당 요청 수(spec 약 190개 기준) |
|---|---|---|
| 1 | 0.885 | 190 |
| 최대 5 | 0.901 | 35.6 |
| 최대 10 | 0.906 | 18.1 |
| 최대 20 | 0.896 | 9.5 |
| 최대 30 | 0.892 | 6.8 |

묶어도 떨어지지 않는다. 오히려 조금 높은데, 소스 10개로는 그 차이에 의미를 둘 수 없다. 최대 30개로 정했다.
글자 수 제한 때문에 실제로는 한 요청에 평균 27개가 들어간다.

### 2단계: 스위트 전체를 줄 세우기

실험 2와 같은 소스 40개에 대해, 이번에는 표본이 아니라 **실패 없는 spec 739개 전부**를 줄 세웠다.
spec은 무작위 순서로 묶었다.

| | Jev(묶음) | 클래스 이름 grep | spec이 실행하는 소스의 수 |
|---|---|---|---|
| AUC | **0.912** [0.881, 0.941] | 0.578 | 0.796 |
| 스위트의 5%만 돌릴 때 잡는 비율 | **70%** [61, 78] | 18% | 31% |
| 스위트의 10% | **76%** [67, 84] | 24% | 48% |
| 스위트의 20% | **84%** [77, 90] | 33% | 65% |
| 95%를 잡는 데 필요한 스위트 비율 | **29%** [21, 39] | 90% | 51% |

돌릴 순서로 보면 이렇다.

| | 평균 |
|---|---|
| 처음 실행하는 spec이 나오는 순위 | 1.08번째 [1.00, 1.18] |
| 앞의 20개 안에 들어오는 비율 | 50% [40, 60] |
| 앞의 50개 | 64% [55, 73] |
| 앞의 100개 | 75% [66, 82] |

40개 소스 중 37개에서 맨 위에 놓인 spec이 실제로 그 소스를 실행하는 spec이었고, 나머지 3개는 두 번째였다.
소스 하나를 실행하는 spec은 중앙값 16개다. 앞의 50개만 돌리면 그중 3분의 2를 본다.

### 비용

| 바뀐 파일 하나당 | 평균 |
|---|---|
| 요청 수 | 27 |
| 입력 토큰 | 59만 |
| 금액 | $0.025 |
| 걸린 시간(동시에 6개씩 요청) | 2.0초 |

쌍마다 따로 물을 때보다 토큰도 절반 아래다. 소스 본문을 spec마다 반복해서 보내지 않기 때문이다.
spec 2,000개짜리 프로젝트라면 요청 75회, 6초, $0.07쯤이다(추정: 비례한다고 가정. 재보지 않았다).

### 묶어서 생기는 부작용은 없는가

- **같은 쌍으로 비교해도 떨어지지 않는다.** 실험 2에서 따로 물었던 쌍만 골라 보면 따로 물을 때 0.898 [0.857, 0.927], 묶었을 때 0.907 [0.871, 0.936]이다.
- **요청 안에서의 위치는 상관없다.** 앞쪽 절반에 놓인 spec의 AUC는 0.906, 뒤쪽 절반은 0.922다.
  실행하지 않는 spec에 준 값의 평균도 0.136과 0.134로 같다.
- **컷오프는 여전히 안전하지 않다.** 스위트 전체에서 Jev ≥ 0.10으로 자르면 무관한 spec의 48%를 돌리면서 영향받는 spec의 8%를 놓친다.
  ≥ 0.05면 놓치는 건 0.2%지만 무관한 spec의 92%를 돌린다. 실험 2의 결론 그대로다.

| 컷오프 | 영향받는 spec 중 선택 | 무관한 spec 중 선택 | 소스당 선택되는 spec 수 |
|---|---|---|---|
| Jev ≥ 0.05 | 99.8% | 92.4% | 687 |
| Jev ≥ 0.10 | 92.0% | 48.2% | 380 |
| Jev ≥ 0.20 | 65.9% | 20.0% | 172 |
| Jev ≥ 0.30 | 49.9% | 9.9% | 95 |
| Jev ≥ 0.50 | 30.0% | 1.1% | 24 |

이 표는 쌍을 전부 합쳐서 센 것이라 실행하는 spec이 많은 소스(`routing_helper.rb`는 342개)가 크게 반영된다.
Jev가 약한 기반 코드가 바로 그런 소스라서 실험 2의 같은 표보다 낮게 나온다.

## 6. affected_tests에 어떻게 쓸까

1. **맵을 대체하거나, spec을 빼는 판단에 쓰면 안 된다.** 맵에 있는 파일은 맵이 정답이다. 실험 1에서 사전 확률이 Jev를 이긴 것도 같은 이야기다.
2. **CI 게이트의 안전망으로도 부족하다.** 맵에 없는 파일이 바뀌었을 때 가장 안전한 대응은 전부 돌리는 것이고,
   Jev로 줄이면 절반을 아끼는 대신 6%를 놓친다. 머지를 막는 CI에서는 받아들이기 어려운 교환이다.
3. **쓸 만한 자리는 빠른 피드백용 순서다.** 맵에 없는 파일이 바뀌었을 때 어차피 전부 돌린다면,
   Jev 값이 높은 순으로 돌리면 앞쪽 5%에서 영향받는 spec의 3분의 2가 실행된다. 아무것도 빼지 않으므로 놓칠 위험이 없다.
   로컬의 pre-push나 "먼저 돌려볼 spec 추천"에도 같은 식으로 쓸 수 있다.
4. **비용과 시간은 걸림돌이 아니다.** spec을 묶어서 물으면 바뀐 파일 하나에 2초, $0.025다(실험 3).
   맵에 없는 파일이 PR에 열 개 있어도 20초다. 맵에 있는 파일은 Jev를 거치지 않으므로 대부분의 PR에서는 호출이 0이다.
5. 지금 `Differ`가 맵에 없는 수정 파일을 말없이 건너뛰는 것은 Jev와 무관하게 고칠 만하다.
   최소한 그런 파일의 목록을 돌려줘서 호출하는 쪽이 "전부 돌리기"로 넘어갈 수 있게 해야 한다.

## 7. 한계

- **프로젝트가 하나다.** Mastodon은 Rails 관례를 잘 따르고 이름이 정직한 코드베이스다.
  메타프로그래밍이 많거나 이름이 제멋대로인 프로젝트에서는 더 낮게 나올 수 있다.
- **Mastodon은 유명한 공개 코드다.** Jev와 Claude 모두 학습 때 봤을 수 있다. 다만 "어떤 spec이 어떤 파일을 실행하는가"는 어디에도 공개된 적이 없는 정보다.
- **잰 것은 "실행하는가"이지 "바뀌면 깨지는가"가 아니다.** 순서를 정하는 용도에서 정말 알고 싶은 것은 후자다.
  실행은 깨지기 위한 필요조건일 뿐이다.
- **정답지에 잡음이 있다.**
  - affected_tests의 RSpec 훅은 예제마다 시작할 때 기록을 비운다. 그래서 `before(:all)`이나 `let_it_be`에서 실행된 코드는 어느 spec에도 붙지 않는다.
  - 뷰를 렌더링하는 request·controller·mailer spec이 실패로 많이 빠졌다. 남은 표본은 모델·서비스·워커·API 쪽으로 기울어 있다.
- **실험 2의 음성은 소스당 150개 표본이다.** 실험 3은 739개 전부를 썼고 결과는 같은 방향이다.
- **실험 3은 spec을 무작위 순서로 묶었다.** 경로 순서대로 묶으면(비슷한 spec이 한 요청에 몰리면) 어떻게 되는지는 재보지 않았다.
- **Claude와의 비교는 40개 spec에 한 번 돌린 것이다.** 묻는 방식도 다르다.

## 8. 다시 돌리려면

```sh
# 1. 맵 만들기 (Mastodon 체크아웃에서, Postgres와 Redis가 떠 있는 상태로)
EXP=~/repos/riseshia/playground/jev-affected-tests
RUBYOPT="-I$EXP/stubs" RAILS_ENV=test AFFECTED_TESTS_MAP_PATH=$EXP/results/mastodon-map.json \
  bundle exec rspec -I ~/repos/riseshia/affected_tests/lib -r $EXP/trace_setup.rb \
  --exclude-pattern "spec/system/**/*_spec.rb" --no-color > $EXP/results/mastodon-rspec.log

# 2. 실험 (Jev 응답은 results/에 저장되어 다시 돌리면 호출 없이 같은 수치가 나온다)
ruby pair_ranking.rb   # 실험 1 + 반복 안정성 + Claude 비교
ruby added_file.rb     # 실험 2
ruby practical.rb      # 실험 3 (added_file.rb를 먼저 돌려야 같은 쌍 비교가 된다)
```

- `stubs/vips.rb`는 이 머신에 libvips 8.13 이상이 없어서 부팅만 통과시키려고 넣은 것이다. libvips가 있으면 `RUBYOPT`를 빼면 된다.
- Jev API 키는 `../jev-cjk/.env`에서 읽는다. 전체 실험에 든 호출은 약 1만 5천 회, 5,400만 토큰, $2.3쯤이다.
